# RE Webapp Factory — User Stories

- **기준 문서:** `docs/PRD.md` (v0.2)
- **작성일:** 2026-09-29
- **상태:** 사용자 확인 완료

---

## 0. 공통 기준

### 사용자

- **1인 메이커(나)** 한 명. GitHub를 기반으로 여러 소규모 개인 웹앱을 직접 기획·제작·운영한다.
- 다중 사용자, 역할, 권한 기능은 v1 범위에서 제외한다.

### 최상위 불변 원칙

모든 스토리에 적용하며, 어떤 경우에도 어기지 않는다.

1. **실제 확인하지 않은 기능·링크·배포·QA 상태를 통과나 완료로 기록하지 않는다.**
2. **업무·개인 프로젝트의 저장소·자산·문서·규칙을 자동으로 가져오거나 혼합하지 않는다.** (탐지할 비공개 식별자는 `config/identifiers.local.json`에만 둔다)

### QA Gate 정의 (5개)

| 순서 | Gate | 검사 범위 |
|---|---|---|
| 1 | Structure | 폴더·저장소·필수 문서 구조 |
| 2 | Design | 계층, 타이포그래피, 색상, 여백, 상호작용 |
| 3 | Responsive & Mobile | 주요 화면 크기 및 iPhone 13 Pro 기준 사용성 |
| 4 | Functional & Accessibility | 핵심 기능, 키보드 조작, 레이블, 대비와 오류 상태 |
| 5 | Deployment | 운영 환경의 기능, 링크, 저장·내보내기와 실제 출력 |

> PRD Must rules에 Functional과 Accessibility가 따로 적힌 부분도 `Functional & Accessibility` 하나의 Gate로 통일한다. 접근성 검사를 생략하는 것은 아니며, 같은 Gate 안에서 **별도 체크리스트**로 검사한다.

### 대시보드 '다음 작업' 결정 방식

**시스템 자동 제안 + 사용자 최종 결정**

- 시스템은 다음 항목을 바탕으로 다음 작업을 자동 제안한다.
  - QA 미통과·미실행 항목
  - 문서 동기화 문제
  - 배포 확인 필요
  - 사용자 승인 대기
- 사용자는 작업을 직접 추가·수정·삭제하고 우선순위를 변경할 수 있다.
- 시스템은 사용자 승인 없이 작업을 완료 처리하지 않는다.

### 스토리 요약

| # | 유저스토리 |
|---|---|
| 1 | 1인 메이커가 기존 웹앱 MD·스타일 가이드를 등록해 공통 기준, 앱별 기준, 참고 자료로 분류하고 확정한다. |

## Story 1 — 기존 자료 정리

**유저스토리**
1인 메이커가 기존 웹앱 MD·스타일 가이드를 등록해 공통 기준, 앱별 기준, 참고 자료로 분류하고 확정한다.

**사용자 가치**
흩어져 있던 MD 파일과 스타일 가이드를 재사용할 수 있는 기준 문서로 정리한다.

**선행 조건**
- 기존 자료(Webapp Factory MD, 스타일 가이드, README, 체크리스트 등)가 제공되어 있다.

**주요 흐름**
1. 기존 Webapp Factory MD, 스타일 가이드, README, 체크리스트를 등록한다.
2. 시스템이 문서를 목적별(`PRD.md`, `design.md`, `AGENTS.md`/`CLAUDE.md`, `qa.md`, `README.md`, `CHANGELOG.md`)로 분류한다.
3. 중복·충돌·누락된 규칙을 표시한다.
4. 사용자가 공통 규칙과 앱별 규칙을 확정한다.
5. 확정된 문서를 기준 자료로 지정한다.

**완료 조건**
- 기존 웹앱 관련 MD와 스타일 가이드가 역할별로 분류되어 있다.
- 각 문서가 공통 기준 / 앱별 기준 / 참고 자료 중 하나로 지정되어 있다.
- 공통 규칙, 앱별 규칙, 충돌 항목이 구분되어 있다.
- 원본이 보존되어 있다.

**필수 승인 조건**
- ✅ 문서 간 충돌을 AI가 임의로 해결하지 않고 사용자에게 확인한다.

**예외·실패 상태**
- 서로 다른 규칙이 있으면 자동으로 합치지 않고 충돌 항목으로 표시한다.
- 규칙이 충돌하거나 최신 문서를 판단할 수 없으면 사용자에게 확인한다.
- 기존 자료의 실제 내용을 확인하기 전에는 새로운 기준으로 추정하거나 덮어쓰지 않는다.

**관련 Must / Do-not 규칙**
- Do-not: 기존 문서의 충돌을 AI가 임의로 해결하지 않는다.
- Do-not: 업무·개인 프로젝트의 저장소, 자산, 문서와 규칙을 자동으로 가져오거나 혼합하지 않는다.
- Source of Truth: 공통 규칙과 앱별 규칙을 분리한다.
- 원본은 보존하고 승인 없이 덮어쓰지 않는다.

**PRD 근거**
시나리오 A, 02 Standards Library, 4. Source of Truth, 기존 자료 반영 대기 목록, v1 완료 조건 1·2

## Story 2 — 새 웹앱 시작

**유저스토리**
1인 메이커가 앱의 목적·사용자·기능을 입력해 5블록 PRD, 표준 구조, 필수 문서, QA 체크리스트로 새 앱을 시작한다.

**사용자 가치**
새 웹앱마다 폴더 구조, 문서, 디자인 기준과 개발 절차가 달라지는 문제를 없애고, 검증된 공통 규칙으로 시작한다.

**선행 조건**
- 기준으로 승인된 문서가 있다. (승인된 문서만 신규 앱 생성에 사용한다.)

**주요 흐름**
1. 앱의 목적, 핵심 사용자와 기능을 입력한다.
2. 5블록 PRD와 표준 프로젝트 구조를 준비한다.
3. 공통 스타일 가이드와 선택한 앱별 규칙을 적용한다.
4. 저장소, 필수 문서, 초기 버전과 QA 체크리스트를 만든다.
5. 사용자가 결과를 확인한 뒤 구현을 시작한다.

**완료 조건**
- 앱이 승인된 공통 구조와 명명 규칙으로 시작되어 있다.
- 5블록 PRD, 표준 폴더 구조, 필수 문서, 초기 버전, 개발 규칙, QA 체크리스트가 준비되어 있다.
- 앱의 저장소 주소, 운영 주소, 현재 버전, 상태와 필수 문서가 등록되어 있다.
- 사용자가 결과를 확인했다.

**예외·실패 상태**
- 앱별 고유 요구사항을 공통 템플릿으로 덮어쓰지 않는다.
- 앱별 규칙이 공통 규칙보다 우선하는 경우 그 차이를 문서에 명시한다.
- 규칙이 충돌하거나 최신 문서를 판단할 수 없으면 사용자에게 확인한다.

**관련 Must / Do-not 규칙**
- Must: 새 앱은 승인된 공통 구조와 명명 규칙으로 시작한다.
- Must: 모든 앱은 저장소 주소, 운영 주소, 현재 버전, 상태와 필수 문서를 등록한다.
- Must: 비밀키, 토큰과 개인정보는 저장소나 문서에 기록하지 않는다.
- Do-not: 앱별 고유 요구사항을 공통 템플릿으로 덮어쓰지 않는다.

**PRD 근거**
시나리오 B, 03 New App Setup, 4. Source of Truth·Must rules, v1 완료 조건 3

## Story 3 — QA Gate 검수

**유저스토리**
1인 메이커가 수정한 앱을 5개 QA Gate(Structure → Design → Responsive & Mobile → Functional & Accessibility → Deployment)로 순서대로 검수한다.

**사용자 가치**
기능 수정 후 모바일·접근성·실제 배포 환경 검수가 빠지는 문제를 막는다.

**선행 조건**
- 변경할 기능과 영향을 받는 화면·문서가 정의되어 있다.
- 구현이 끝났다.

**주요 흐름**
1. Structure Gate: 폴더·저장소·필수 문서 구조를 검사한다.
2. Design Gate: 계층, 타이포그래피, 색상, 여백, 상호작용을 검사한다.
3. Responsive & Mobile Gate: 주요 화면 크기와 iPhone 13 Pro 기준 사용성을 검사한다.
4. Functional & Accessibility Gate: 핵심 기능과 오류 상태를 검사하고, 접근성(키보드 조작, 레이블, 대비)은 별도 체크리스트로 검사한다.
5. Deployment Gate: 운영 환경의 기능, 링크, 저장·내보내기와 실제 출력을 검사한다.
6. 미통과 항목을 해결한다.

**완료 조건**
- 해당 앱이 5개 QA Gate를 모두 거쳤다.
- 각 Gate의 통과 여부가 실제 확인 결과로 기록되어 있다.
- 접근성 체크리스트가 실행되어 있다.

**예외·실패 상태**
- 미통과 항목이 있으면 해결 전까지 완료로 표시하지 않는다.
- 실행하지 않은 Gate나 실제 확인하지 않은 항목은 통과로 기록하지 않는다.
- QA 미통과·미실행 항목은 대시보드 '다음 작업' 제안 대상이 된다.

**관련 Must / Do-not 규칙**
- Must: 릴리스 전 Structure, Design, Responsive & Mobile, Functional & Accessibility, Deployment QA를 수행한다.
- Must: 실제 확인하지 않은 기능, 링크와 배포 상태는 통과로 기록하지 않는다.
- Do-not: QA 미통과나 문서 불일치 상태를 숨긴 채 완료로 표시하지 않는다.
- Do-not: 문서만 갱신하고 실제 앱 동작 확인을 생략하지 않는다.

**PRD 근거**
시나리오 C 1·2·4, 04 QA Gate, 4. Must rules·Do-not rules, v1 완료 조건 4

## Story 4 — 릴리스·문서 동기화·배포 기록

**유저스토리**
1인 메이커가 버전·README·CHANGELOG·운영 URL이 서로 맞는지 확인하고, 최종 승인 후 배포 결과를 기록한다.

**사용자 가치**
코드 변경과 버전 번호, README, CHANGELOG가 어긋나는 문제를 없앤다.

**선행 조건**
- 해당 변경이 QA Gate를 거쳤다.

**주요 흐름**
1. 버전 번호, README, CHANGELOG와 관련 가이드를 함께 갱신한다.
2. 코드 변경과 버전 번호, README, CHANGELOG, 관련 가이드, 운영 URL 사이의 일치 여부를 확인한다.
3. 미통과 항목과 문서 불일치를 해결한다.
4. 사용자가 최종 확인한다.
5. 배포하고 운영 주소와 결과를 기록한다.
6. 릴리스 결과, 미해결 문제와 롤백 참고사항을 기록한다.

**완료 조건**
- 코드, 버전, README, CHANGELOG와 운영 URL이 일치하는 릴리스 기록이 남아 있다.
- 완료 보고에 앱 이름, 버전, 운영 주소, 변경 요약과 QA 결과가 포함되어 있다.
- 릴리스 결과, 미해결 문제와 롤백 참고사항이 기록되어 있다.

**필수 승인 조건**
- ✅ 배포·삭제·강제 덮어쓰기 등 되돌리기 어려운 작업은 사용자 확인 후 실행한다.

**예외·실패 상태**
- 문서 불일치가 남아 있으면 숨긴 채 완료로 표시하지 않는다.
- 사용자 최종 확인이 없으면 배포하지 않는다.
- 실제 확인하지 않은 배포 상태는 통과로 기록하지 않는다.
- 자동 롤백은 v1 범위가 아니므로 롤백 참고사항만 기록한다.

**관련 Must / Do-not 규칙**
- Must: 코드가 바뀌면 버전 번호, README, CHANGELOG와 관련 기준 문서도 함께 검토한다.
- Must: 완료 보고에는 앱 이름, 버전, 운영 주소, 변경 요약과 QA 결과를 포함한다.
- Must: 삭제, 강제 덮어쓰기, 공개 배포 등 되돌리기 어려운 작업은 사용자 확인 후 실행한다.
- Must: 비밀키, 토큰과 개인정보는 저장소나 문서에 기록하지 않는다.
- Do-not: QA 미통과나 문서 불일치 상태를 숨긴 채 완료로 표시하지 않는다.

**PRD 근거**
시나리오 C 3~5, 05 Release & Documentation Sync, 4. Must rules·Do-not rules, 5. 제외(자동 롤백), v1 완료 조건 5

## Story 5 — 앱 레지스트리·대시보드

**유저스토리**
1인 메이커가 대시보드에서 모든 앱의 저장소, 운영 URL, 버전, 배포·QA 상태, 다음 작업을 한눈에 확인한다.

**사용자 가치**
여러 앱의 저장소, 운영 주소, 현재 버전과 유지보수 상태를 한곳에서 확인한다.

**선행 조건**
- 앱이 레지스트리에 등록되어 있다.

**주요 흐름**
1. 대시보드에서 각 앱의 이름, 목적, GitHub 저장소, 운영 URL, 현재 버전, 최근 변경일, 배포 상태, QA 상태와 다음 작업을 본다.
2. 시스템이 QA 미통과·미실행 항목, 문서 동기화 문제, 배포 확인 필요, 사용자 승인 대기를 바탕으로 다음 작업을 자동 제안한다.
3. 사용자가 작업을 직접 추가·수정·삭제하고 우선순위를 변경한다.

**완료 조건**
- 등록된 모든 앱의 표시 항목이 대시보드에 보인다.
- 앱마다 다음 작업이 제안되어 있고, 사용자가 최종 결정할 수 있다.

**예외·실패 상태**
- 시스템은 사용자 승인 없이 작업을 완료 처리하지 않는다.
- 실제 확인하지 않은 배포·QA 상태는 통과로 표시하지 않는다.
- 운영 로그·분석·비용의 실시간 통합 모니터링은 v1 범위가 아니다.

**관련 Must / Do-not 규칙**
- Must: 모든 앱은 저장소 주소, 운영 주소, 현재 버전, 상태와 필수 문서를 등록한다.
- Must: 실제 확인하지 않은 기능, 링크와 배포 상태는 통과로 기록하지 않는다.
- Do-not: QA 미통과나 문서 불일치 상태를 숨긴 채 완료로 표시하지 않는다.

**PRD 근거**
01 App Registry / Dashboard, 1. 해결하려는 문제·목표, 5. 포함(앱 레지스트리와 상태 대시보드)·제외(실시간 통합 모니터링)
