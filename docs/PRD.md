# RE Webapp Factory — PRD

- **문서 버전:** v0.2
- **문서 상태:** 기존 자료 통합 전 기준안
- **프로젝트 유형:** 개인 웹앱 제작·운영 하네스
- **사용 범위:** 개인 GitHub 웹앱 전용

> **프로젝트 경계**  
> RE Webapp Factory는 개인 웹앱을 만들고 운영하기 위한 독립 시스템이다. WORK_PROJECT 회사 업무, WORK_PROJECT 저장소·디자인 시스템·자산 및 IHIRI 창작·브랜드 시스템과 연결하거나 혼합하지 않는다. 다른 프로젝트의 자료는 사용자가 특정 자료의 참조를 명시적으로 요청한 경우에만 제한적으로 사용한다.

---

## 1. 프로젝트 정의와 목표

### 한 줄 정의

**RE Webapp Factory는 기존에 축적한 웹앱 제작 규칙과 스타일 가이드를 기준으로, 개인 GitHub 웹앱의 생성·구현·QA·버전 관리·문서화·배포·유지보수를 일관되게 운영하는 개인 개발 하네스다.**

### 해결하려는 문제

- 새 웹앱마다 폴더 구조, 문서, 디자인 기준과 개발 절차가 달라진다.
- 기존에 만든 MD 파일과 스타일 가이드가 흩어져 있어 재사용하기 어렵다.
- 기능 수정 후 모바일·접근성·실제 배포 환경 검수가 빠지기 쉽다.
- 코드 변경과 버전 번호, README, CHANGELOG가 어긋난다.
- 여러 앱의 저장소, 운영 주소, 현재 버전과 유지보수 상태를 한눈에 보기 어렵다.

### 목표

- 기존 웹앱 관련 문서를 수집하고 역할별 기준 문서로 정리한다.
- 새 앱을 공통 구조와 검증된 규칙으로 시작한다.
- 앱별 고유 디자인과 공통 디자인 원칙을 구분한다.
- 모든 릴리스가 QA, 버전, 문서, 배포 주소와 연결되게 한다.
- 각 앱의 현재 상태와 다음 유지보수 작업을 한곳에서 확인한다.

### 비목표

- 아이디어, 제품 전략, 디자인 판단을 AI가 전부 대신하지 않는다.
- 무인 코드 생성·자동 배포·자동 롤백 시스템을 목표로 하지 않는다.
- WORK_PROJECT·IHIRI 또는 다른 조직 프로젝트의 통합 관리 도구로 확장하지 않는다.

## 2. 사용자와 핵심 시나리오

### 주 사용자

GitHub를 기반으로 여러 소규모 개인 웹앱을 직접 기획·제작·운영하는 1인 메이커인 나.

### 시나리오 A — 기존 자료 정리

1. 기존 Webapp Factory MD, 스타일 가이드, README, 체크리스트를 등록한다.
2. 시스템이 문서를 목적별로 분류한다.
3. 중복·충돌·누락된 규칙을 표시한다.
4. 사용자가 공통 규칙과 앱별 규칙을 확정한다.
5. 확정된 문서를 기준 자료로 지정한다.

### 시나리오 B — 새 웹앱 시작

1. 앱의 목적, 핵심 사용자와 기능을 입력한다.
2. 5블록 PRD와 표준 프로젝트 구조를 준비한다.
3. 공통 스타일 가이드와 선택한 앱별 규칙을 적용한다.
4. 저장소, 필수 문서, 초기 버전과 QA 체크리스트를 만든다.
5. 사용자가 결과를 확인한 뒤 구현을 시작한다.

### 시나리오 C — 수정·검수·릴리스

1. 변경할 기능과 영향을 받는 화면·문서를 정의한다.
2. 구현 후 기능·디자인·모바일·접근성·배포 환경 QA를 수행한다.
3. 버전 번호, README, CHANGELOG와 관련 가이드를 함께 갱신한다.
4. 미통과 항목과 문서 불일치를 해결한다.
5. 사용자의 최종 확인 후 배포하고 운영 주소와 결과를 기록한다.

## 3. 핵심 화면·모듈

### 01. App Registry / Dashboard

각 앱의 이름, 목적, GitHub 저장소, 운영 URL, 현재 버전, 최근 변경일, 배포 상태, QA 상태와 다음 작업을 보여준다.

### 02. Standards Library

기존 및 신규 MD 파일을 다음 역할로 분류·관리한다.

- `PRD.md`: 제품 목적, 사용자, 범위, 기능
- `design.md`: 색상, 타이포그래피, 여백, 컴포넌트, 반응형 원칙
- `AGENTS.md` / `CLAUDE.md`: AI 작업 규칙과 프로젝트 경계
- `qa.md`: 기능·디자인·모바일·접근성·배포 검수 기준
- `README.md`: 설치, 실행, 사용법과 운영 주소
- `CHANGELOG.md`: 버전별 변경 내역

각 문서는 **공통 기준 / 앱별 기준 / 참고 자료** 중 하나로 지정한다. 서로 다른 규칙은 자동으로 합치지 않고 충돌 항목으로 표시한다.

### 03. New App Setup

앱 정보와 선택한 기준 문서를 바탕으로 5블록 PRD, 표준 폴더 구조, 필수 문서, 초기 버전, 개발 규칙과 QA 체크리스트를 준비한다.

### 04. QA Gate

다섯 가지 Gate를 순서대로 관리한다.

1. **Structure:** 폴더·저장소·필수 문서 구조
2. **Design:** 계층, 타이포그래피, 색상, 여백, 상호작용
3. **Responsive & Mobile:** 주요 화면 크기 및 iPhone 13 Pro 기준 사용성
4. **Functional & Accessibility:** 핵심 기능, 키보드 조작, 레이블, 대비와 오류 상태
5. **Deployment:** 운영 환경의 기능, 링크, 저장·내보내기와 실제 출력

### 05. Release & Documentation Sync

코드 변경과 버전 번호, README, CHANGELOG, 관련 가이드 및 운영 URL 사이의 일치 여부를 확인한다. 릴리스 결과, 미해결 문제와 롤백 참고사항을 기록한다.

## 4. 기준 문서와 운영 원칙

### Source of Truth

- 기준으로 승인된 문서만 신규 앱 생성과 QA에 사용한다.
- 공통 규칙과 앱별 규칙을 분리한다.
- 앱별 규칙은 해당 앱에서 공통 규칙보다 우선할 수 있지만, 그 차이를 문서에 명시한다.
- 규칙이 충돌하거나 최신 문서를 판단할 수 없으면 사용자에게 확인한다.
- 기존 자료의 실제 내용을 확인하기 전에는 새로운 기준으로 추정하거나 덮어쓰지 않는다.

### Must rules

- 모든 앱은 저장소 주소, 운영 주소, 현재 버전, 상태와 필수 문서를 등록한다.
- 새 앱은 승인된 공통 구조와 명명 규칙으로 시작한다.
- 릴리스 전 Structure, Design, Mobile, Functional, Accessibility, Deployment QA를 수행한다.
- 코드가 바뀌면 버전 번호, README, CHANGELOG와 관련 기준 문서도 함께 검토한다.
- 완료 보고에는 앱 이름, 버전, 운영 주소, 변경 요약과 QA 결과를 포함한다.
- 실제 확인하지 않은 기능, 링크와 배포 상태는 통과로 기록하지 않는다.
- 비밀키, 토큰과 개인정보는 저장소나 문서에 기록하지 않는다.
- 삭제, 강제 덮어쓰기, 공개 배포 등 되돌리기 어려운 작업은 사용자 확인 후 실행한다.

### Do-not rules

- WORK_PROJECT 및 IHIRI의 저장소, 자산, 문서와 규칙을 자동으로 가져오거나 혼합하지 않는다.
- 기존 문서의 충돌을 AI가 임의로 해결하지 않는다.
- QA 미통과나 문서 불일치 상태를 숨긴 채 완료로 표시하지 않는다.
- 앱별 고유 요구사항을 공통 템플릿으로 덮어쓰지 않는다.
- 문서만 갱신하고 실제 앱 동작 확인을 생략하지 않는다.

### 기본 우선순위

```text
사용자의 현재 명시적 결정
→ 해당 앱의 승인된 규칙
→ RE Webapp Factory 공통 규칙
→ 참고 자료
```

## 5. v1 범위와 완료 조건

### v1 핵심 흐름

```text
기존 자료 등록·분류
→ 앱 등록 또는 신규 앱 설정
→ 구현
→ QA Gate
→ 버전·문서 동기화
→ 사용자 승인
→ 배포 결과 기록
```

### 포함

- 기존 Webapp Factory MD와 스타일 가이드 등록·분류
- 공통 규칙과 앱별 규칙 구분
- 규칙 중복·충돌·누락 목록 작성
- 앱 레지스트리와 상태 대시보드
- 5블록 PRD 및 기본 문서 템플릿
- 표준 프로젝트 구조 체크리스트
- 기능·디자인·모바일·접근성·배포 QA 체크리스트
- 버전, README, CHANGELOG 동기화 점검
- 운영 URL과 릴리스 결과 기록

### 제외

- 실제 기존 문서를 확인하기 전의 스타일 규칙 확정
- 완전 자동 코드 생성과 무인 배포
- 다중 사용자 권한 및 조직 협업
- 운영 로그·분석·비용의 실시간 통합 모니터링
- 자동 롤백과 장애 복구
- WORK_PROJECT·IHIRI 프로젝트 연동

### v1 완료 조건

다음 조건을 모두 충족하면 v1을 완료한 것으로 본다.

1. 기존 웹앱 관련 MD와 스타일 가이드가 역할별로 분류되어 있다.
2. 공통 규칙과 앱별 규칙, 충돌 항목이 구분되어 있다.
3. 개인 웹앱 하나를 등록하거나 표준 구조로 새로 시작할 수 있다.
4. 해당 앱이 모든 QA Gate를 거친다.
5. 코드, 버전, README, CHANGELOG와 운영 URL이 일치하는 릴리스 기록을 남길 수 있다.

## 기존 자료 반영 대기 목록

아래 자료가 제공되면 이 PRD와 기준 문서 구조를 다시 검토한다.

- 기존 Webapp Factory 관련 `.md` 파일
- 개인 웹앱 공통 스타일 가이드
- 기존 앱별 `README.md`, `CHANGELOG.md`, `design.md`
- 사용 중인 폴더·저장소 명명 규칙
- 기존 QA·배포 체크리스트

자료를 확인한 뒤 각 항목을 **PRD 요구사항 / 공통 디자인 규칙 / 앱별 규칙 / AI 행동 규칙 / QA 기준 / 참고 자료**로 나누며, 원본은 보존하고 승인 없이 덮어쓰지 않는다.
